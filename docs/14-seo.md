# SEO — договорённости и текущая реализация

Как устроено SEO в этом проекте (Next.js Pages Router) и какие правила закладываем по
умолчанию. Документ совмещает **договорённости студии** (по итогам аудита проектов) и **текущее
состояние сборки** — что уже работает из коробки, а что настраивается под проект.

- Виджет: [`src/widgets/seo-layout/`](../src/widgets/seo-layout/) (`OgTags` + `Favicons` + `LdJson`)
- Цепочка fallback: [`og-tags/utils.ts`](../src/widgets/seo-layout/og-tags/utils.ts) (`mergeSeoData`)
- Мета-теги: [`og-tags/og-tags.tsx`](../src/widgets/seo-layout/og-tags/og-tags.tsx)
- Типы SEO-данных: [`src/shared/types/seo.ts`](../src/shared/types/seo.ts)
- robots.txt / sitemap: [`src/pages/robots.txt.ts`](../src/pages/robots.txt.ts), [12-sitemap.md](./12-sitemap.md)
- Плейбук для агентов: скилл `seo` (`.claude/skills/seo/SKILL.md`)

## Главный принцип

SEO **не собирается вручную на каждой странице**. У каждого типа страницы — предсказуемое поведение и
**цепочка fallback**. Редактор может переопределить любое поле, но сайт обязан отдавать валидное SEO и
без единого заполненного поля. Пустые строки и строки из пробелов считаются **отсутствующим** значением.

```
ручное поле (CMS) → данные страницы/сущности → родитель/категория → глобальные настройки (commonData.seo) → дефолты сборки (APP_INFO)
```

## Как это работает сейчас

`SeoLayout` рендерится один раз в [`_app.tsx`](../src/pages/_app.tsx) и получает два входа из props
страницы:

- `commonSeoData = cms.commonData.seo` — глобальное SEO сайта (из `getCommonData`, кэшируется).
- `pageSeoData = cms.pageSeoData` — SEO конкретной страницы (верх цепочки).

`mergeSeoData({ commonSeoData, pageSeoData })` резолвит каждое поле по цепочке и возвращает
`{ title, description, keywords, ogImage, ogImageAlt, ogImageWidth, ogImageHeight, siteName, theme,
noindex, origin }`. `OgTags` рендерит из этого: `title`, `description`, `keywords`, **`robots`**,
`theme-color`, полный набор `og:*` (включая `og:site_name`, `og:image` + `alt`/`width`/`height`),
`twitter:*`, `<link rel="canonical">`.

Что уже сделано корректно:

| Поведение | Где | Деталь |
|---|---|---|
| og:image абсолютный | `utils.ts` `toAbsoluteUrl` | относительные `/og.png`, `/uploads/...` → абсолютный публичный URL |
| canonical абсолютный | `og-tags.tsx` | `origin + asPath`, query отрезается (`split("?")[0]`) |
| robots по режиму | `og-tags.tsx` | `index,follow` только если окружение открыто И страница не `noindex`; иначе `noindex,nofollow` |
| индексируется только прод | `app.ts` `APP_ALLOW_INDEXING` | `NEXT_PUBLIC_APP_ENV === "production"` — **тот же сигнал**, что в `robots.txt.ts` |
| noindex на уровне страницы | `Seo.noindex` + `utils.ts` | булев флаг страницы, OR с глобальным |
| og:image alt/width/height | `utils.ts` + `og-tags.tsx` | alt из картинки → заголовок; размеры из картинки → 1200×630 |
| og:site_name | `utils.ts` `siteName` | глобальный SEO-title → дефолт → домен |

Форма SEO-данных — тип [`Seo`](../src/shared/types/seo.ts): `title`, `description`,
`ogImage`, `keywords`, `theme` (цвет), `structuredData`, `noindex` (bool). Раньше это было
зеркало компонента CMS; теперь значения приходят из кода страницы.

### Добавить SEO новой странице

1. Собрать объект `Seo` в `getServerSideProps` страницы.
2. Положить его в `props.cms.pageSeoData`.

`_app.tsx` уже читает `cms.pageSeoData` и передаёт в `SeoLayout` — свои `<Head>` в странице
**не добавляем**.

## Договорённости студии (проектные дефолты)

Ниже — что закладываем по умолчанию. Часть уже в коде (см. таблицу выше), часть настраивается **под
проект** — не изобретать расходящееся поведение.

### 1. Title и description
Главная = бренд + короткое позиционирование. Внутренние = `Страница | Сайт` (дедуп уже в
`mergeSeoData`). Карточки каталога — коммерческие параметры (тип, площадь, цена, регион), если есть.
Статьи/события — заголовок, лид, автор, дата/тип. Не резать молча — предупреждать.

### 2. Canonical и дубли
Canonical всегда абсолютный. Разделы и SEO-фильтры — как **path** (`/catalog/kitchens/white/`),
не случайный query. Обычные фильтры/сортировки — `noindex,follow` или canonical на базу. SEO-фильтры —
только по allow-list, у каждого свои slug/title/description/canonical/правило sitemap.

**Аллоу-лист параметров (реализовано).** В canonical попадают только параметры, явно разрешённые
для конкретного маршрута — карта `CANONICAL_PARAMS` в
[`og-tags/canonical.ts`](../src/widgets/seo-layout/og-tags/canonical.ts). Всё остальное (UTM,
`fbclid`, `gclid`, debug, preview) отбрасывается автоматически. Аллоу-лист, а не блок-лист: список
рекламных меток бесконечен, а список значимых параметров короткий и известен заранее.

**Пагинация.** Страница пагинации канонизируется **сама на себя**, а не на базовый листинг — иначе
поисковик считает её дублем первой страницы и товары со второй и дальше могут не попасть в индекс.
Реализовано для `/products` (`?page`):

- `?page=1`, `?page=abc`, `?page=-5` → canonical на базовый URL (это тот же контент);
- `?page=02` и `?page=2` → один canonical (нормализация);
- порядок параметров не влияет на результат;
- у страниц пагинации свой `title` (`… — страница N`), чтобы не дублировать заголовки;
- `PAGINATION_NOINDEX` переключает стратегию на `noindex,follow` для страниц 2+, если SEO-специалист
  проекта не хочет видеть листинги в индексе.

⚠️ **Разрешая параметр в `CANONICAL_PARAMS`, убедись, что роут действительно отдаёт по нему другой
контент.** Разрешить параметр, который сервер игнорирует, — значит завести дубль: два индексируемых
URL с одинаковым содержимым. И ссылки пагинации обязаны быть настоящими `<a href>` — иначе бот не
обойдёт глубокие страницы, каким бы правильным ни был canonical.

### 3. Open Graph
У каждой индексируемой страницы — валидная OG-картинка: публичная, абсолютная, без cookies/авторизации,
1200×630 (1.91:1). Fallback: картинка страницы → картинка сущности → глобальная OG. `alt`/`width`/
`height` отдаём (сделано). Динамические OG с текстом/ценой — позже, базовая должна работать сразу.

### 4. Robots и индексация
Прод открыт, тест/preview закрыты (сделано через env-гейт). У каждой страницы понятный режим
(`index,follow` / `noindex,follow` / `noindex,nofollow`). Поиск, служебные, обычные фильтры — по
умолчанию не индексировать. Страница с `noindex` **не** попадает в sitemap. Ручное исключение — флаг
`noindex` в CMS.

### 5. Sitemap
Строится из реальных публичных страниц, только канонические и индексируемые, `lastmod` из `updatedAt`,
sitemap index для крупных, связи локалей для мультиязычных. **Реализовано** — см. [12-sitemap.md](./12-sitemap.md).

**Исключение `noindex` тоже реализовано:** записи коллекций фильтруются при обходе
(`populate: { seo: { fields: ["noindex"] } }`), статические маршруты — по реестру `STATIC_PAGE_SEO`
(`src/shared/api/sitemap/static-pages.ts`; **регистрируй там страницу, когда даёшь ей SEO-компонент**).
Фильтр намеренно fail-open: исключает только явный `true`, поэтому отсутствие `seo` или ошибка
чтения не выкидывают реальную страницу из карты.

### 6. Schema.org / JSON-LD
Базовую разметку генерировать автоматически из реальных данных страницы; ручной JSON — только
как дополнение. Сегодня `LdJson` отдаёт **только** ручной `structuredData` — **автогенерация под проект**.

`structuredData` допускает и строку, и готовый объект, поэтому
[`LdJson`](../src/widgets/seo-layout/ld-json/ld-json.tsx) не пробрасывает её в разметку, а
**парсит → проверяет → сериализует заново**:

- **невалидный JSON не выводится** и пишется в лог — битая разметка, отданная молча, хуже отсутствующей;
- **каждый `<` заменяется юникод-escape**, поэтому `</script>` внутри значения не может закрыть тег
  (парсер декодирует обратно — значение не меняется). Без этого внешнее содержимое в `<script>` —
  готовый вектор инъекции;
- объект на входе тоже поддержан — на случай, если разметку соберут в коде.

⚠️ Не обходи этот путь: не подставляй контент из CMS напрямую в `<script>`.
Типы: `WebSite`, `Organization`/`LocalBusiness`/`Store`, `CollectionPage`/`ItemList`/`BreadcrumbList`,
`Product`/`Offer`/`Service`, `Article`/`BlogPosting`/`NewsArticle`, `Event`. **Не** выводить рейтинги,
отзывы, цены, наличие, которых реально нет на странице.

### 7. Данные организации
Один структурный блок организации в глобальных данных (название, юр. название, описание, логотип,
телефон, email, адрес, координаты, часы, соцсети). Переиспользовать для футера, контактов, schema.org;
соцсети → `sameAs`. Пустые поля в schema.org не выводить. Сейчас `commonData` содержит `socials`/
`contacts`, но не полный структурный блок — **добавляется под проект**.

### 8. Каталог, фильтры, карточки
Разделять SEO-фильтры и пользовательские. Пользовательские — не индексировать. SEO-фильтры —
осознанно: свой URL/заголовок/описание/текст/флаг sitemap. На листинге schema.org для списка текущей
страницы, не всего каталога. На карточке — данные самой карточки; цена/наличие совпадают с видимыми.

### 9. Медиа, статьи, события
У каждой статьи/новости/события свои title/description/canonical/OG. Хранить автора, дату публикации,
дату обновления, лид, главное изображение (статьи); дату начала/окончания, место, статус, организатора
(события). При миграции архива — карта старых→новых URL, 301-редиректы, без дублей.

### 10. Мультиязычность
Per-locale canonical + `hreflang` + связи локалей в sitemap. Не вести на пустой/неэквивалентный
перевод. **Не реализовано** (пока одна локаль) — **добавляется под проект**.

## 11. Контроль качества (перед релизом)

Проверять **HTML, который получает бот** (view-source / curl), а не только отрисованную страницу, на
типовом наборе URL: главная, каталог, обычный фильтр, SEO-фильтр, карточка, статья, событие, контакты,
пагинация, 404, preview. Для каждого: `<title>`, `description`, `canonical` (абсолютный), `robots`,
набор `og:*`, JSON-LD, наличие/отсутствие в `sitemap.xml`.

Считать **ошибкой**: пустые SEO-данные, относительные OG-картинки, OG за авторизацией/cookies,
`noindex`-страницы в sitemap, индексируемые технические страницы.

```bash
curl -s localhost:3000/ | grep -iE '<title>|og:image|canonical|name="robots"'
# прод: robots.txt открывает сайт; на тесте/preview обязателен Disallow: /
```

Перед релизом — проверить карточки ссылок в мессенджерах и валидаторах соцсетей; schema.org прогнать
валидатором (особенно организация, каталог, товар, статья, событие).
